# Coin ratings and reviews

## Architecture and behavior

This feature extends the React/Vite application and Supabase PostgreSQL backend. It uses the existing `coins.id` UUID, existing Supabase owner authorization, React Query, Lucide icons, and English/German/Greek translations. No framework or separate coin database is introduced.

Migration `003_coin_reviews.sql` adds `coin_reviews`, a private idempotency/rate-limit receipt table, a public read RPC, a server-only submission RPC, and an owner-only search RPC. Coin deletion cascades to associated reviews and receipts, matching the existing image/reference behavior. Owner moderation can change only status or delete rows: it cannot reassign a review to another coin.

Visitors submit a required display name (1–100 characters), an integer rating (1–5), and optional text (up to 2,000 characters). Email and customer accounts are not collected because anonymous reviews do not require them. Submission time is generated by PostgreSQL as `timestamptz`; the UI formats dates with the selected language and browser timezone. React renders comments as text, never HTML.

New submissions are pending. Only approved reviews on published coins appear publicly. Rating-only records contribute to rating counts, averages and distribution; written-review counts are separate. Public pages show 10 records at a time with deterministic newest/oldest/highest/lowest sorting. The average is rounded to one decimal place in PostgreSQL; percentages derive from returned approved counts. No-rating averages are null. Query invalidation uses the existing realtime broadcast channel, with a 30-second review refresh fallback.

The owner dashboard links to `/admin/reviews`. Search matches literal substrings in coin names and display names; filtering supports coin, rating and status. Moderation is protected by the existing route guard, PostgreSQL RLS, and column privileges. The admin list is paginated in groups of 20.

## Deployment

1. Back up the Supabase database. Apply `003_coin_reviews.sql` after migrations 001 and 002 using the existing SQL Editor workflow or the project's Supabase migration tooling. It adds new objects without changing existing coin records.
2. Create a Cloudflare Turnstile widget, registering the production and any preview hostnames. Set public build variable `VITE_TURNSTILE_SITE_KEY`. Keep `VITE_DEMO_MODE=false` for the connected site. Missing configuration disables submissions; demo mode does not persist or fabricate reviews.
3. Configure Edge Function secrets: `TURNSTILE_SECRET_KEY`, `REVIEW_RATE_SECRET` (a cryptographically random secret of at least 32 bytes), and `REVIEW_ORIGINS` (comma-separated exact frontend origins, without trailing slashes). Existing `SUPABASE_URL` and server-only `SUPABASE_SERVICE_ROLE_KEY` are provided by Supabase. Never put server secrets in Vite variables, Git, or browser code.
4. Deploy `submit-review` with `supabase functions deploy submit-review`. Its `verify_jwt=false` configuration permits anonymous requests; the function performs mandatory server-side Turnstile checks for hostname and action, validates inputs and origin, and calls the database RPC with a server-only key. Public visitors cannot call that write RPC directly.
5. Build and deploy the frontend and `public/_headers`. The CSP permits the Turnstile script and iframe while retaining existing restrictions. Check the real hosted challenge, which cannot be fully verified by local mocks.
6. On staging, verify that the Supabase gateway supplies and sanitizes `x-forwarded-for` as expected; do not deploy the function behind a proxy that accepts client-forged forwarded addresses. If a trusted address is missing, submissions fail closed. The function HMAC-hashes this address with the server secret; raw addresses are not stored in the review tables. Shared network users share the five-new-reviews-per-hour limit.
7. Submit a review for a real published coin, approve it as owner, and check the public summary. Reject/delete it and confirm exclusion. Test another coin, a hidden coin, invalid input, direct RPC attempts, a non-owner account, repeated clicks and a sixth submission from the same address. No live migration or deployment was performed during implementation.

The function follows [Supabase's server secret guidance](https://supabase.com/docs/guides/functions/secrets) and [Cloudflare's mandatory server-side token validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

## API contract

`POST /functions/v1/submit-review` accepts JSON:

```json
{
  "submission_id": "client-generated UUID, reused for an unchanged retry",
  "coin_id": "existing published coin UUID",
  "display_name": "Collector",
  "rating": 5,
  "review_text": "Optional comment",
  "website": "",
  "token": "fresh Turnstile token"
}
```

Success returns HTTP 201, `{"status":"pending"}`. Errors are `{"error":"message"}` with 400 (invalid input), 403 (origin/challenge failure), 404 (unavailable coin), 405 (wrong method), 413 (oversized request), 429 (rate limit, `Retry-After: 3600`), or 503 (configuration/upstream/database failure). Tokens are one-use; retries require a new challenge, but reuse the submission UUID for unchanged data. The database serializes requests by receipt and actor to prevent concurrent duplicate writes and rate-limit races.

`POST /rest/v1/rpc/get_coin_reviews` accepts `p_coin_id`, `p_sort` (`newest`, `oldest`, `highest`, `lowest`) and `p_page` (1–10,000). It returns `items`, `total`, `written_count`, nullable `average`, and `distribution` counts keyed by 1–5. Items contain only `id`, `display_name`, `rating`, `review_text`, and `created_at`. Hidden/missing coins raise `P0002` through PostgREST. Invalid pagination/sorting raise validation errors. Public reads use the existing publishable-key client.

Owner clients call `search_admin_reviews` with `p_coin_id` (nullable), `p_rating` (nullable), `p_status` (empty or pending/approved/rejected), `p_query` (up to 200 characters), and `p_page`. Result: `items` (with coin names and moderation status) and `total`. Owner updates use `PATCH /rest/v1/coin_reviews?id=eq.<review-id>` with `{"status":"approved"}` or `{"status":"rejected"}`; deletion uses `DELETE` on that path. Supabase bearer authentication and RLS apply; anonymous/non-owner moderation is denied.

## Privacy, retention and SEO

The form explains publication of display names and review content and asks visitors to omit private information. Owner deletion permanently removes the review and its associated private receipt; deleting a coin removes both as well. Idempotency/rate-limit receipts are cleaned after seven days when new submissions arrive. For a strict time-based retention policy during idle periods, schedule this SQL in the existing database operations process:

```sql
delete from private.review_receipts where created_at < now() - interval '7 days';
```

Reviews themselves remain until removed by the owner or coin deletion. Establish the site's published retention/deletion policy and use the existing contact address for deletion requests. Receipts no longer protect against duplicate retries once removed. Server logs and Turnstile processing have their own retention policies.

The current site is a personal specimen catalogue with no sale offers or Product schema. Product/AggregateRating structured data is therefore deferred rather than presenting catalogue specimens as sale products. If commerce is introduced, add one accurate Product schema using approved, visible counts only, after checking current search-engine eligibility. No fake ratings or production fixtures are included.

Review tests cover required/invalid input, malicious text rendering, keyboard selection, rating-only submission, repeated clicks, retry receipts, sorting, pagination and moderation.
